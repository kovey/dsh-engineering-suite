# 被否决的设计（Rejected designs）

这份清单记录**我们刻意不做的事，以及为什么**。它的用途不是自证清白，而是让后来人（人和模型）在提出同一个想法时，
能先看到"这件事在什么前提下被拒过、拒的理由是否还成立"。参考设计
[dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) 用一节 `Rejected concepts` 做同样的事，
本文件是我们在更大范围（15 个插件、六个阶段）上的对应物。

**读法**：每条都写"否决的是什么 / 理由 / **什么条件下可以重新考虑**"。最后一项最重要——设计不是信仰，
前提变了就该重新评估，而不是把清单当教条。

## 一、执行与运行面

| 否决 | 理由 | 重新考虑的前提 |
|---|---|---|
| 自带 **Source 监听栈**（长轮询 GitHub/飞书、admission table、bot 名单、订阅交接） | 这是"主动接活"的入口系统，属于别的产品面；我们已有 `dsh-chat-interaction` 作为通道，重做会与官方能力打架并制造两套真相 | 官方不再提供通道能力，或我们需要"无人在场也接活"的形态（那时应作为**独立插件**，不塞进治理层） |
| **每个工作项一个会话 + 一个目录**（Ticket/Executor/WorkerSlots） | 执行隔离归宿主（`subagent`、`experimental-worktree`）；治理层越界会变成半个 orchestrator | 宿主收回这些能力 |
| **SQLite 单写者 + 目录锁 + 24×7 守护进程** | 我们是会话内插件、台账是 `.dsh/**` 文件；引入守护进程会推翻信任根模型（谁写 `.dsh` 变成后台进程） | 出现"必须 24×7 运行"的需求，且能接受信任根改由守护进程持有 |
| **定时器驱动的重放**（outbox/effects 的后台调度） | 同上：没有常驻进程。我们的重放是**机会式**的（装配时、下次动作前），空闲会话不重试——这是**已写明的边界** | 有了常驻运行时 |
| 在 host 侧**锁死 Executor 全部工具**来表示"失败/阻塞" | 会连人自己在会话里动手、以及恢复后的报告一起拒掉；暂停自动输入就够了 | 永不考虑（这属于把手段当目的） |

## 二、授权与判断

| 否决 | 理由 | 重新考虑的前提 |
|---|---|---|
| 让官方 **auto-review**（LLM 评审）**接管授权** | 概率判断不能作为放行的依据，违反"证据优先于声明"。代码级核实：它只返回 `deny`/`ask`/`cancel`，从不 `allow`——所以它只能收紧，不能授权 | 永不考虑作为授权来源；**可以考虑**作为附加限制（今天已如此） |
| **`auto` 作为默认接受模式**（推断工作自动接受） | 与我们"默认 fail-closed、人工审批是硬门"冲突 | 某类低风险工作可以被**规则**显式纳入，且先经过 observe 影子期 |
| **规格可以自带 `mode: observe`** | 规格是模型可写的，允许它给自己的预算设影子 = **自我豁免** | 永不考虑 |
| 用**自由文本**推断"在等人" | 需要结构化事实；我们的对应物是结构化字段（`whyYou`）与台账状态 | 永不考虑 |
| 跨 Source 的**身份映射**（谁是同一个人的两个账号） | 身份是各来源自己的事实；跨源映射写进代码会制造"看不见的权限合并" | 由团队的提示词/技能描述承担，而非代码 |
| **取消在飞工作**以响应策略变更 | 会留下半成品；参考设计也只是"记录并通知受影响项"。我们的做法是**失效 + 恢复前重校验 + 只能新开 mission** | 永不考虑（除非能保证半成品可安全回收） |

## 三、检索与知识

| 否决 | 理由 | 重新考虑的前提 |
|---|---|---|
| **嵌入/向量库**、任何网络侧嵌入服务 | 不可复现、不可审计；同一输入必须得到逐字节相同的索引 | 需要跨语言同义召回，且能接受"检索结果不可复现"的代价（届时作为**可选后端**，默认仍是词法） |
| 把**审计行与 git 历史**塞进知识库 | 它们是行为记录不是知识；塞进去会让"回答"看起来有据但其实在复述日志 | 有明确的"考古"用例，且能标出证据等级 |
| 让知识库片段**影响门禁结论** | 上下文不是授权（见 ARCHITECTURE §5.23）。文档可以建议，不能放行 | 永不考虑 |

## 四、交付与验证

| 否决 | 理由 | 重新考虑的前提 |
|---|---|---|
| 把**合并/评审策略**写进套件 | 那是目标仓库的规范；套件只提供"允许谁做什么"的机制，不规定"什么算好代码" | 永不考虑（违反分层） |
| **`plugin-manager`/`config-editor` 顺带负责验证** | 安装 ≠ 工作正常。验证必须由能失败的东西做（我们的 `verify.sh`/`doctor`/E2E） | 永不考虑 |
| 用**静默截断**处理超长报告/超限配置 | 静默截断让人以为看到了全部 | 永不考虑（超限必须拒绝并说明） |
| **精确锁版** peer 依赖 | 会让每次宿主 rc 都要重发插件，且掩盖"跨线未验证"这件事；`>=0.2.0-rc.1 <0.2.2-0` 表达的是"同线可升级、跨线必须重新验证" | 出现破坏性 API 变更（那时也只需收紧上界） |

## 五、流程与交互

| 否决 | 理由 | 重新考虑的前提 |
|---|---|---|
| 让 **IM 成为授权来源** | 通道只改变"人在哪里被问"，不改变"什么算允许"（§5.23） | 永不考虑 |
| **重发**一个没人回答的问题 | 这是拿噪音换注意力；我们的做法是**降频/撤回**，且撤回 ≠ 允许 | 有"必须强提醒"的运维需求（应作为**人配置的规则**，并计入策略版本） |
| 在**健康状态**里也占版面 | 健康状态必须一行；问题必须可行动 | 永不考虑 |
| 把 **task-active 标记写到全局 `~/.dsh`** | 任务会话与项目强相关，必须按项目隔离 | 永不考虑 |
